# Versioned Customer Deployment Repository Contract

**Parent Issue**: #15
**Epic**: #13
**Status**: Implementation

## Overview

This document defines the stable on-disk and Git contract for a private, customer-owned ownCloud deployment repository. The repository is the auditable desired deployment state and serves as the single source of truth for deployment configuration.

## Repository Structure

```
customer-deployment-repo/
├── owncloud.yaml                    # User-owned deployment intent (PRIMARY)
├── overlays/                        # Supported user customizations
│   ├── custom-config.yaml           # User-provided configuration overlays
│   ├── custom-env.env               # User-provided environment variables
│   └── ...
├── owncloud.lock.json               # Exact renderer, catalogue, component and image digests
├── generated/                       # Deterministic deployment output
│   ├── docker-compose.yml           # Generated Docker Compose file
│   ├── ocis.yml                     # Generated oCIS configuration
│   ├── helm/                        # Generated Helm values (if Kubernetes)
│   │   └── values.yaml
│   ├── ansible/                     # Generated Ansible inventory/vars
│   │   ├── inventory.yml
│   │   └── group_vars/
│   └── kubernetes/                  # Generated Kubernetes manifests
│       └── ...
├── .get-owncloud/
│   ├── metadata.json                # Repository format and applied migration state
│   └── migrations/                  # Applied migration records
│       └── <migration-id>.json
├── .gitignore                       # Standard Git ignore patterns
├── README.md                        # Repository-specific documentation
└── docs/                           # Optional user documentation
    └── ...
```

## File Specifications

### 1. `owncloud.yaml` - User-Owned Deployment Intent

**Purpose**: Primary user-owned configuration file defining deployment intent.

**Schema**: Must conform to `https://get.owncloud.com/schema/deployment.schema.json`

**Ownership**: User/customer - this is the authoritative source of truth for user intent.

**Properties**:
- `apiVersion`: Repository format version (e.g., `get.owncloud.com/v1alpha1`)
- `purpose`: `evaluation` or `production`
- `maturity`: `community-preview` or `production`
- `ocisVersion`: Pinned oCIS version
- `target`: Runtime (`docker`, `podman`, `kubernetes`) and manager (`direct`, `ansible`, `argocd`)
- `workload`: Sizing parameters
- `identity`: Identity configuration
- `storage`: Storage configuration
- `office`: Office integration configuration
- `networking`: Network configuration
- `mail`: Mail configuration (optional)
- `features`: Feature flags
- `security`: Security settings
- `updates`: Update policy

**Example**:
```yaml
apiVersion: get.owncloud.com/v1alpha1
purpose: production
target:
  runtime: docker
  manager: direct
workload:
  registeredUsers: 100
  storedDataGiB: 500
  annualGrowthPercent: 20
identity:
  mode: external-oidc
  issuer: https://id.acme-corp.net/realms/owncloud
  clientId: web
storage:
  mode: ocis
  filesystem: xfs
  dataPath: /srv/owncloud/data
  configPath: /srv/owncloud/config
office:
  mode: collabora
  deployment: bundled
networking:
  domain: cloud.acme-corp.net
  collaboraDomain: office.acme-corp.net
tls:
  mode: acme
  email: hostmaster@acme-corp.net
```

### 2. `overlays/` - Supported User Customizations

**Purpose**: User-provided customizations that override or extend generated configuration.

**Ownership**: User/customer

**Validation**: All overlays are validated against the fully resolved output and cannot bypass product policy.

**Supported Files**:
- `*.yaml` / `*.yml`: Kubernetes/Helm value overlays
- `*.env`: Environment variable overrides
- `*.json`: JSON configuration patches

**Constraints**:
- Cannot override security-critical settings (TLS mode, EULA acceptance)
- Cannot disable required policy enforcement
- Must be declarative and deterministic
- All references to secrets must use secret references, not plaintext

### 3. `owncloud.lock.json` - Exact Dependency Lock

**Purpose**: Exact renderer, catalogue, component and image digests for reproducible builds.

**Ownership**: Generated by the configurator, committed by user after review

**Schema**:
```json
{
  "repositoryFormatVersion": "1.0.0",
  "generatedAt": "2026-01-01T00:00:00Z",
  "configuratorVersion": "v1.0.0",
  "catalogueVersion": "2026.08.22.2",
  "profileHash": "sha256:abc123...",
  "renderer": {
    "type": "docker-compose",
    "version": "1.0.0"
  },
  "components": {
    "ocis": {
      "version": "8.2.0",
      "gitCommit": "42f7fdcfee2714cb14eedb36509f74ef205703f9",
      "image": "docker.io/owncloud/ocis@sha256:8c053ea63fc15b9788d55725b5d3abd9632dd89abfcb8a127e0c85acdd4ec2b4"
    },
    "collabora": {
      "version": "23.05.0",
      "image": "docker.io/collabora/code@sha256:abc123..."
    }
  },
  "policy": {
    "eulaSha256": "f608b0819964232648c5fb6b22a4d58310331128ad645ab158a35ef1790e2148",
    "maturity": "production"
  },
  "sizing": {
    "minimum": {"cpu": 2, "ramMiB": 4096, "diskGiB": 5},
    "recommended": {"cpu": 4, "ramMiB": 8192, "diskGiB": 10}
  }
}
```

### 4. `generated/` - Deterministic Deployment Output

**Purpose**: Generated deployment artifacts that are deterministic for a given profile and lock.

**Ownership**: Generated by the configurator, committed for auditability

**Structure**:
- Files are organized by deployment family (docker-compose, helm, ansible, kubernetes)
- All files are read-only from the user's perspective
- Manual changes are detected and fail closed

**Drift Detection**:
- Each generated file contains a header comment with its generation hash
- The updater verifies all generated files match the current lock
- Drift is reported with specific file paths and remediation steps

### 5. `.get-owncloud/metadata.json` - Repository Metadata

**Purpose**: Repository format version and applied migration state.

**Schema**:
```json
{
  "repositoryFormatVersion": "1.0.0",
  "createdAt": "2026-01-01T00:00:00Z",
  "lastUpdated": "2026-01-01T00:00:00Z",
  "configuratorVersion": "v1.0.0",
  "migrations": [
    {
      "id": "migration-001",
      "appliedAt": "2026-01-01T00:00:00Z",
      "fromVersion": "0.9.0",
      "toVersion": "1.0.0",
      "description": "Initial repository format"
    }
  ],
  "deploymentId": "uuid:abc-123-def-456",
  "customerId": "customer-abc-123"
}
```

## Canonical Ordering and Serialization

### File Order
Files MUST be committed in the following order to ensure deterministic Git history:

1. `.get-owncloud/metadata.json`
2. `owncloud.yaml`
3. `overlays/*.yaml` (sorted alphabetically)
4. `overlays/*.yml` (sorted alphabetically)
5. `overlays/*.env` (sorted alphabetically)
6. `owncloud.lock.json`
7. `generated/` (recursively, sorted alphabetically)
8. `.gitignore`
9. `README.md`

### Serialization Rules

1. **YAML**:
   - Use 2-space indentation
   - No trailing whitespace
   - Keys sorted alphabetically within each object
   - String values quoted if they contain special characters
   - No comments in generated files

2. **JSON**:
   - Use 2-space indentation
   - Keys sorted alphabetically
   - No trailing commas
   - UTF-8 encoding

3. **Determinism**:
   - Same input profile + same catalogue version = byte-identical output
   - Generated files include a hash of their input in a header comment
   - Lock file includes SHA-256 hash of the profile

## Forward/Backward Compatibility

### Schema Support Windows

| Repository Format Version | Configurator Version | Support Status |
| --- | --- | --- |
| 1.0.0 | >= v1.0.0 | Current |
| 0.9.x | >= v0.9.0, < v1.0.0 | Deprecated |

### Compatibility Rules

1. **Forward Compatibility**: A newer configurator can read older repository formats
2. **Backward Compatibility**: An older configurator will reject newer repository formats with a clear error
3. **Migration Path**: Each repository format version has a defined migration path to the next version
4. **Deprecation**: Deprecated formats are supported for 6 months after the next major version release

### Migration Process

1. Updater detects repository format version
2. Checks for available migrations
3. Applies migrations in order
4. Updates `.get-owncloud/metadata.json` with migration record
5. Commits migration changes to a dedicated branch
6. Opens PR for user review

## Ownership Markers

### File-Level Ownership

| File/Path | Owner | Mutable | Description |
| --- | --- | --- | --- |
| `owncloud.yaml` | User | Yes | Primary intent |
| `overlays/*` | User | Yes | Customizations |
| `owncloud.lock.json` | System | No | Dependency lock |
| `generated/*` | System | No | Generated output |
| `.get-owncloud/*` | System | No | Metadata |
| `.gitignore` | System | No | Git patterns |
| `README.md` | User | Yes | Documentation |

### Drift Detection

1. **Generated Files**: Any manual change to `generated/` or `owncloud.lock.json` is detected
2. **Detection Method**: SHA-256 hash comparison against expected content
3. **Response**: Fail closed with remediation instructions
4. **Remediation**: User must either:
   - Revert the change and regenerate
   - Update the profile and regenerate
   - Contact support if the change is intentional

## Legacy Bundle Import

### Conversion Process

1. Extract ZIP bundle to a temporary directory
2. Parse `profile.json` and `secrets.json` (if present)
3. Create new repository structure:
   - `owncloud.yaml` from `profile.json`
   - `owncloud.lock.json` from bundle metadata
   - `generated/` from bundle contents
   - `.get-owncloud/metadata.json` with migration record
4. Validate round-trip: regenerate and compare
5. If validation fails, stop with actionable diagnostics
6. If validation passes, commit with migration history

### Preservation Guarantees

- All user-owned fields survive regeneration unchanged
- All secrets remain as secret references (never plaintext)
- Runtime behavior is identical to the original bundle
- Deployment ID is preserved for tracking

## Validation

### JSON Schema Validation

Every committed control file MUST be validated against its schema:

- `owncloud.yaml` -> `deployment.schema.json`
- `owncloud.lock.json` -> `lock.schema.json` (to be defined)
- `.get-owncloud/metadata.json` -> `metadata.schema.json` (to be defined)

### Drift Scanner

A drift scanner runs in CI and verifies:

1. All generated files match their expected content
2. No plaintext secrets are committed
3. No forbidden files are present (databases, backups, credentials)
4. All required files are present
5. Repository format version is supported

### Forbidden Patterns

The following patterns are forbidden and will cause validation to fail:

- Plaintext passwords or API keys
- Private keys or certificates
- Registry credentials
- Runtime databases or database dumps
- Backup files
- Core system files (e.g., `/etc/`, `/var/`)
- Binary files (except explicitly allowed images)
- Symlinks

## Policy Enforcement

### Storage Policy
- NFS must be verified as NFSv4.2
- Only `ocis` or `s3ng` storage modes are allowed
- POSIX filesystem metadata is required for `s3ng`

### Identity Policy
- Embedded IDP/IDM limited to 20 users maximum
- External OIDC requires LDAPS for production
- All OIDC endpoints must use HTTPS

### Office Integration Policy
- Collabora is the only supported office integration
- Bundled or external deployment modes only

### EULA Policy
- EULA acknowledgement is mandatory for runnable output
- EULA hash must match the pinned version
- Acceptance is recorded in the lock file

### Update Policy
- All updates are gated by policy checks
- Security patches can be applied automatically (if configured)
- Major version updates require manual approval
- Rollback is always possible to the previous approved state
